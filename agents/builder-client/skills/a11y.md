# Skill — Accessibility (a11y)

## Activate when

- **Always active on UI PRs** as a Phase 5 (self-review) check during Builder-Client's own dev cycle
- Explicit invocation: `@client-agent a11y audit <route>` / Linear ticket with `a11y` label
- Guardian's `design-system` + `a11y` review on incoming PR webhooks (Guardian-side; coordinate)

## Specialized knowledge

- **WCAG 2.1 AA** as the working bar (AAA is aspirational; AA is the operational target)
- **Common a11y bugs in React/RN code**:
  - `<div onClick>` instead of `<button>` (loses keyboard semantics + screen-reader announcement)
  - Missing form labels (`<label htmlFor>` or `aria-label`)
  - Hidden focus indicators (custom `:focus` removing the outline without replacement)
  - `display: none` on focused elements (focus disappears silently)
  - Color-only conveying information (red/green status without a text/icon counterpart)
  - Autoplay video without controls
  - Motion without `prefers-reduced-motion` respect
  - Missing alt text or improper alt (alt=" " when image is meaningful; alt="<long descriptive text>" on decorative images)
- **Tools** — axe-core / @axe-core/react / Playwright a11y plugin / Lighthouse a11y. Project-specific choice loaded from `STACK.md`.
- **Mobile a11y** — VoiceOver labels (`accessibilityLabel`, `accessibilityHint`, `accessibilityRole`), focus order in screens, dynamic type support.

## Procedure

1. Identify what changed in the PR (component / route / screen).
2. Run the project's automated a11y tool on the affected surface(s).
3. Categorize findings:
   - **Critical / serious** (color contrast failures, missing labels, keyboard traps, focus management bugs) — **must fix before merge**.
   - **Moderate** (suboptimal alt text, redundant aria, missing landmarks) — fix if cheap; document if expensive.
   - **Minor** (style preferences from the tool) — usually ignore unless they're false positives that mask real issues.
4. Fix critical/serious issues in the same PR (narrow patches — aria attributes, alt text, semantic markup swaps, contrast adjustments).
5. Add a11y assertions to the component tests where useful (e.g. "button has accessible name").
6. Report the axe summary in the PR description.

## Output format (in the PR description)

```markdown
## a11y audit
- **Tool**: axe-core via @axe-core/react
- **Surfaces audited**: <list>
- **Findings**:
  - Critical: 0
  - Serious: 0
  - Moderate: 2 (see fixes in commit `<sha>`)
  - Minor: 1 (suppressed — false positive on `aria-hidden` decoration)

✅ Cleared for merge from an a11y perspective.
```

## Examples

> **Finding**: axe reports "color-contrast" failure on the secondary button — text color #888 against background #fff is 3.5:1, below the 4.5:1 AA bar.
>
> **Action**: check the project's design tokens; if a higher-contrast token exists (e.g. `text-muted` at #666 = 5.7:1), swap to that. If not, propose adding a new higher-contrast token in the design-system update.

> **Finding**: clickable `<div>` in the navigation that handles `onClick`.
>
> **Action**: convert to `<button>` with `onClick`; styling stays the same (we strip browser defaults globally). Adds keyboard semantics and screen-reader announcement.

## Pushback discipline

**a11y is non-negotiable.** If a reviewer wants to skip an a11y check or rationalize away an axe finding, decline politely and explain the user impact:

> "The contrast finding is real — 3.5:1 contrast means a user with even mild low vision will struggle to read this. We have a token (`text-muted`) that hits 5.7:1 and looks nearly identical. Pushing the swap unless you have evidence the visual difference is product-critical."

## Outputs

- a11y-only commits within the same PR (narrow patches: aria attributes, semantic HTML swaps, contrast token swaps)
- PR description section with the audit summary
- Updates to `dev-team-state/projects/<project>/builder-client/a11y/audit-baseline.md` when the project's a11y state changes materially

## Escalation

- **A11y findings would require a design change** (not just code) → post screenshots + finding details, ping the human responsible for design + propose a Claude Design pre-fill if a redesign is warranted.
- **Tool is reporting false positives consistently** → flag for a tool config update; don't suppress in code without good reason.
- **A reviewer insists on skipping a critical/serious finding** → decline politely; escalate to a human owner. a11y findings of critical/serious severity block merge by policy.

## What this skill does NOT do

- Skip a11y findings to ship faster.
- Make purely visual/aesthetic decisions about how to fix a contrast issue (suggest options; defer to design).
- Fix substantive design issues that require a re-design (those need Claude Design with a human).
- Refactor entire components for a11y reasons (small narrow patches only — substantive refactors get tickets for `frontend` skill).
